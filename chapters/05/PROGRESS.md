## Found on the way, feeding §5.2

**Cyclic resource declarations are a deliberate divergence**, per the user, not a
gap to close. The two cases moved to `suites/viper/divergence/`, a new directory
whose README states the difference and which E3 must not read as an
incompleteness. Silicon verifies both, confirmed.

- `self_unfolding_predicate.vpr` — `unfolding P(x) in ...` inside `P`'s own body.
- `function_under_own_predicate.vpr` — a function whose precondition is `P`,
  called inside `P`'s body.

Both are **whole-file** `[PIPELINE-ERROR]`s, so §5.2.1 must scope its
per-declaration reporting claim to typecheck and translation, and say that the
resource analysis rejects a file.

**How often it bites, measured** (`experiments/08_silver_corpus.py`, new): over
the 1430 Viper files of Silver's own test suite, **3 trip the rejection (0.2%)**,
and none of the three models anything — one is a predicate the Silver authors
named `strange`, the other two are regression tests against Silicon issue
numbers 0092 and 0172.

A third case I filed was **my own bad Viper, now deleted**:
`unfolding_in_postcondition.vpr` had a postcondition that is not well-defined,
and Silicon rejects it with the same complaint Helium gives. Helium handles the
shape correctly once the guard is stated inside the `unfolding`.


## Pin correction, 30 August

`vendor/silver-oxide` was pinned at `8e31c8c`; `b43026e` ("Add reporting
unsupported members") is the next commit on `backend-blocks` and is what makes
Helium name a refused construct per declaration. The pin is now `b43026e` and

container types were whole-file parse errors, and **inhale-exhale verified** —
unsoundly. Every number in `results/2026-08-30-8e31c8c/` is at the old pin and
must be re-taken, the E8 corpus classification included.

function.


## §5.2.1 done, 30 August

Suite: `suites/features/tutorial/{containers,termination,inhale-exhale,wands,
quantified-permissions}` — 51 probes, one per construct the Viper tutorial names.
Runner: `experiments/01_tutorial_features.py`. Tables:
`report/generated/features.typ` and `features-counts.typ`.

- **Silicon is the gate.** Six of the first 51 probes were rejected by Silicon
  and rewritten before any number was taken. The runner exits non-zero and
  reports `BAD PROBES` if a probe stops matching its `//@ silicon:` header.
- **44 refusals, 44 name the construct, 0 whole-file parse errors.** That is
  §5.2.1's claim and it now holds across all four refusal areas.
- **`#` is not Viper.** Multiset multiplicity is `e in ms`, which yields an Int.
  My earlier note that the `#` operator was the last whole-file parse error was
  wrong — `#` is a separator in Silver's grammar, so Helium's parse error there
  is correct. The exception list is empty.
- **Termination is not a refusal** and is out of the table: all 7 forms parse and
  are dropped. `function bad(n: Int): Int decreases n { bad(n) + 1 }` reports
  `[OK]` where Silicon rejects it. The only gap in the five areas a reader cannot
  see. `assert false` after it is still rejected, so it does not spread.
- **First construct wins.** The tutorial's own quantified-permission idiom
  `forall x: Ref :: x in xs ==> acc(x.f)` is reported as `Set`, not as a
  quantified permission. Stated in the prose.

Also fixed: the lock recorded the **system** Rust (1.94.0-beta.2), not the one
`rust-toolchain.toml` pins. `env.py` now runs `rustc`/`cargo` inside the
submodule and records the channel: Helium builds with **1.95.0-nightly**.

## §5.4 done, 01 September

Written from `results/2026-09-01-0147de4/raw.jsonl`, the same sweep §5.3
quotes. New generator: `experiments/11_report_attribution.py`, writes
`report/generated/attribution-{tiers-rust,tiers-viper-perf,scalars}.typ`.

**Found and fixed on the way, all in `heval/`:**

- `report.tier_table` never filtered by suite, so `tiers-rust.typ` and
  `tiers-viper-perf.typ` were identical and shared a Typst label — a hard
  compile error had they ever been `#include`d together. Now takes
  `suite_name` and filters on it.
- `report.tier_table` also summed every kept repetition instead of one row
  per case, overcounting obligations by however many reps a case had lying
  around (harmless while every case had exactly 3, fatal once some had 5-6 —
  see next item). Now dedups by case first.
- `06_tier_breakdown.py` had a second, dead `def main()` above the live one
  (unreachable, and itself broken — referenced undefined `path`/`suite_name`).
  Deleted.
- Neither `06_tier_breakdown.py` nor `07_rule_costs.py` supported `--only`/
  `--exclude` on their live-verification path, so `--suite rust` always loaded
  every `.vpr` under `suites/rust/vpr/`, not just the 11-file performance
  corpus — silently mixing in the `enum_v*`/`depth_*` scaling-grid files that
  live in the same directory for an unrelated experiment. **This bit twice**:
  once profiling (added ~5835 spurious rows to the pinned sweep, since
  cleaned out by filtering on case name), and once ablating (a `SILVER_OXIDE_
  DROP_RULES` run over the full 35-file directory, killed once noticed). Both
  scripts now take `--only`/`--exclude` like `02_rust_corpus.py` already does.
  **Lesson for next time: run a case-count sanity check before trusting any
  `--suite` live-verification path in this repo — `suite.load` never filters
  to a curated subset on its own.**

**The rule ablation is hand-recorded, not regenerated.** Ablating a rule means
re-verifying the corpus twice per rule, and one of the three ablated here
(`ite-reduce`) times out on 10 of 11 files when dropped — not something to
re-run inside a table generator on every sweep. The numbers live in
`ABLATION` at the top of `11_report_attribution.py`, with the exact command
that reproduces them.
